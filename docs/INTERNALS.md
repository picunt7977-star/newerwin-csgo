# newerwin — как это устроено

Основа — [Osiris](https://github.com/danielkrupinski/Osiris), ветка `csgo` (MIT). Поверх добавлено:
рейджбот, автоволл, DT, антиаимы с десинком, меню в стиле gamesense.

## Граница

- Чит работает **только** если игра запущена с `-insecure` (`Source/InsecureGate.h`).
  С этим флагом движок сам не пускает на VAC-серверы — значит, только insecure/хвх-серверы
  и локальная игра.
- Никакого обхода или сокрытия от VAC. Репортбот вырезан.

## Сборка и запуск

```
./csgo-hvh.sh            # собрать и показать параметры запуска
```

Параметры запуска в Steam (CS:GO legacy):

```
SDL_VIDEODRIVER=x11 LD_PRELOAD="$LD_PRELOAD:/путь/к/newerwin-csgo/build/Source/libOsiris.so" %command% -insecure
```

`SDL_VIDEODRIVER=x11` обязателен: в Hyprland задано `wayland,x11,windows` (синтаксис SDL3),
встроенная в игру SDL2 его не понимает и игра падает на старте — даже без чита.

Меню — `Insert`. Чит поднимается через ~5 секунд после главного меню игры.

## Резольвер по слоям анимации

Из `DT_CSPlayer` сервер вырезает `m_flPoseParameter` (там лежал бы `body_yaw` — готовый ответ),
но **не** вырезает `m_AnimOverlay`: 13 слоёв анимации игрока приходят по сети такими, какими их
посчитал сервер — то есть из **настоящего** угла ног врага. На этом и построен резольвер:

1. `FRAME_NET_UPDATE_POSTDATAUPDATE_START` — единственный момент, когда сетевые слои ещё не
   перезатёрла клиентская анимация. Снимаем их (`Resolver.cpp: onNetUpdate`).
2. Берём `animstate` врага, подставляем угол ног-кандидат (сетка ±максимальный десинк, `m_flLowerBodyYawTarget`,
   наш прошлый ответ, крайние углы от прошлого взгляда — на случай джиттера) и зовём ту же функцию движка,
   что зовёт сам клиент: `CCSGOPlayerAnimState::Update`.
3. Сравниваем полученные слои с сетевыми. Ошибку по каждому полю (`m_flWeight`, `m_flCycle`,
   `m_flPlaybackRate`, `m_nSequence`) делим на разброс этого поля между кандидатами — так в счёт идут
   только те слои, которые вообще зависят от угла ног (доворот ног, стрейф, lean), а не шум и кванты.
4. Побеждает кандидат с минимальной ошибкой; отдаём **угол ног после обновления** — движок сам
   обрезал его по максимальному десинку, значит он физически возможен. Уверенность считается
   **по стороне, а не по узлу**: соседние узлы сетки стоят в 5-6° друг от друга и дают почти
   одинаковую ошибку, поэтому сравниваются лучшие узлы правой и левой половин
   (`ResolverScoring.h: scoreSides`) — туда входит по десятку узлов, случайно выиграть целой
   половиной трудно. Уверенность дополнительно режется, когда сигнал всего один
   (одно поле одного слоя — по логам 29.10 так было почти всегда, с «уверенностью» до 97%).
4a. Если победил угол почти по взгляду, а враг при этом чокает — это шум: движок доворачивает к
   взгляду сразу всех кандидатов, их слои совпадают, и выигрывает случайный. Берём лучший узел
   выигравшей половины. Десинка без чока не бывает, а чок без десинка бессмыслен.
4b. **Якорь по LBY.** Пока враг стоит, сервер раз в 1.1 с (и сразу при повороте больше 35°)
   ставит `m_flLowerBodyYawTarget` равным его настоящему взгляду, а animstate в тот же момент
   доворачивает ноги ровно на LBY. На обновлении, где LBY сдвинулся, угол ног известен точно —
   слои не разбираем вообще, уверенность 100%. Это как раз те обновления, где слои молчали.
5. Состояние после лучшего кандидата остаётся «тенью»: с него считается следующее обновление,
   чтобы наша история анимации шла в ногу с серверной.
6. Поверх угла — перебор вариантов коррекции (см. ниже): слои врут на дефенсиве и лютом джиттере,
   а величину десинка систематически занижают.

Рейджбот собирает скелет записи ровно под этот угол (`Ragebot.cpp: rebuildByAnimation`), а крайние углы
(`±maxDesync`) оставляет для безопасных точек. Если слои молчат (враг стоит, ноги не крутятся) или
сервер их не шлёт — остаётся старый путь: фристенд-догадка плюс перебор стороны по промахам.

Что разобрано из `client_client.so` (клиент 13546, linux64) и где это в коде:

| Что | Значение | Где |
|---|---|---|
| `CCSGOPlayerAnimState::Update(this, bool force, float yaw, float pitch)` | `0xf45560` | паттерн в `LinuxClientPatternFinder` |
| `m_pPlayerAnimState` в `C_CSPlayer` | `+0xa250` | берётся из байтов вызова Update |
| размер animstate | `0x3b8` | `CSGO/AnimState.h` |
| `m_flEyeYaw` / `m_flPitch` / `m_flFootYaw` | `0x8c` / `0x90` / `0x94` | там же |
| `m_flLastUpdateTime` / кадр / дельта | `0x80` / `0x84` / `0x88` | там же |
| `m_flDuckAmount`, доли скорости, `m_flMaxBodyYawDegrees` | `0xb8`, `0x10c`/`0x110`, `0x3a8` | там же (формула максимального десинка) |
| `CAnimationLayer` | шаг `0x48`, `m_nOrder 0x18` … `m_flCycle 0x30` | `CSGO/AnimationLayer.h` |
| `m_AnimOverlay` | офсет из netvar игры | `Entity::animOverlayVector` |

Проверки на всякий случай: офсет animstate берётся только из разобранного кода (не нашёлся — всё,
что читает animstate, выключается), поля проверяются на правдоподобие, `animstate->player` должен
совпасть с игроком, а сетевые слои — пройти проверку на вменяемость. При любом несовпадении в консоль
летит `[newerwin]`-сообщение и резольвер откатывается на геометрию.

В консоли при первом обновлении печатается строка с найденными офсетами и тем, приходят ли сетевые
слои; на каждый промах по вине резольвера — его дельта, уверенность, ошибка и число сигналов.
Под прицелом индикатор `R +12°  64%` (угол ног относительно взгляда и уверенность).

## Что показал разбор лога 29.10 (653 выстрела)

| путь | попал |
|---|---|
| запись «свежая» + сторона от слоёв | 78% |
| сторона «без резольвера (не десинкает)» | 69% |
| любая запись + сторона от слоёв | 62% |
| «память слоёв» | 37% |
| **«угадано» (фристенд)** | **35%, 243 выстрела** |
| «обратно» | 25% |
| «угадано low» / «без поворота» | 8-11% |
| **запись «вперёд» (предсказанная)** | **32%, 368 выстрелов из 653** |

Отсюда правки: половинные режимы и «без поворота» из перебора убраны; память стороны больше не
учится на находках с низкой уверенностью; на предсказанной записи с неизвестной стороной
безопасные точки теперь **требуются**, а не предпочитаются (если под них не набирается мин. урон,
второй проход всё равно стреляет как раньше).

Предсказанной записью идёт 56% выстрелов (свежая отстаёт на 250-340 мс при пинге 55 мс и не
проходит окно отката: заряженный DT добавляет к тикбейсу +93 мс). Но **само предсказание тут ни
при чём**: `проверка предсказания` в том же логе говорит «пуля попала бы в запись +0 обн.» в 76
случаях из 112, а ошибка предсказания меньше 2 юнитов в 75 из 136. Момент и позицию мы угадываем,
пуля уходит в `plus`/`minus` — промах по стороне десинка. `aheadBias` калибруется сам и стоит
на -1 (перелётов вдвое больше недолётов — он это уже учёл).

Значит, узкое место — сторона на предсказанной записи: там взгляд врага за 300 мс уходит на 60°,
резольвер про будущий момент ничего сказать не может, и остаётся фристенд-догадка (29%).
Лечится не окном отката, а тем, чтобы угол от слоёв находился чаще (якорь по LBY) и чтобы при
неизвестной стороне стрелять точками, общими для обеих.

## Известные ограничения

- Резольвер по слоям и анимфикс разобраны под конкретную сборку клиента (13546): на другой сборке
  они сами себя выключат — останутся подмена поз и перебор стороны по промахам.
- Пока враг стоит и ноги не крутятся, слои про угол ног ничего не говорят — там работает фристенд-догадка.
- DT зависит от `sv_maxusrcmdprocessticks` сервера (по умолчанию 16 — работает).

## Дефенсив (переписан 07.11, по модели Neverlose/Persistence)

Окно дефенсива — тики, когда наш `m_nTickBase` ниже максимума, который сервер уже видел: новых
записей лагкомпа по нам не пишется (`RecordDataIntoTrack` не кладёт запись с simtime ≤ головы),
и углы этих тиков нельзя ни бектрекнуть, ни разрезольвить. Откат делает сам сервер в
`CBasePlayer::AdjustPlayerTimeBase`, когда пачка команд уводит `nEstimatedFinalTick` за
`sv_clockcorrection_msecs` от идеального — поэтому сдвигать надо весь заряд, на 2 тиках откат не
срабатывает.

Что было не так до переписывания:

1. **Окно требовало DT.** `defensiveAaOn` = галка **и** `doubleTapEnabled()`, а `defensiveAllowed()`
   = `!fastFire()`. С DT в быстрой стрельбе рывки были запрещены, без DT дефенсив не включался
   вообще — работал только узкий случай «DT в режиме Дефенсив / скаут-AWP». Теперь заряд у
   дефенсива свой, `defensiveAllowed()` отдаёт его только быстрой стрельбе DT.
2. **Рывок просили, когда враг нас УЖЕ видел** (`requestBreakLc` выходил по `!threat`) — запись
   лагкомпа на выглядывании он к этому моменту получал. Теперь достаточно живого врага в 2000 ед.:
   заряд успевает набраться заранее, цикл «рывок → окно → зарядка → рывок» идёт сам.
3. **Синтетические окна.** При Force LC окно выдумывалось, когда лагкомп по нам писался: враг
   получал в запись ровно скрытые углы (голова вверх, спин) и забирал их бектреком. Убраны.
4. **Хвост окна уходил наружу.** `defensiveTicksLeft()` возвращал сырое `max − tickbase − 1` из
   снапшота, устаревшее на RTT: последние ~4 тика «окна» сервер уже писал в лагкомп. Теперь окно
   ведётся в своём времени (от своего сдвига) и подтверждение сервера берётся минус RTT в тиках.

## Extended yaw (переписан 07.11, схема из `extendedyaw.lua`, -anfisov/gamesense)

Было: предсказание таймера LBY (0.22 с после остановки, дальше раз в 1.1 с) и флик ровно в тик
обновления, с подстройкой прогноза по присланному LBY и пингу. Прогноз ехал от каждого сдвига DT и
потерянной команды — флик уходил мимо, тело оставалось в центре.

Стало (как в Persistence): таймера нет вовсе. Сервер ставит LBY = взгляд **каждую** команду, в
которой мы двигаемся, — этим и пользуемся. Чокнутая команда несёт yaw, уведённый на `extendedYaw` в
сторону десинка, и на ней же идёт микродвижение (`forwardmove 0.1` + `IN_FORWARD`); отправленная
команда несёт настоящий взгляд. Без extended yaw микродвижение остаётся прежним (`sidemove ±1.1`) и
служит наоборот — не давать серверу обновлять LBY.

Из их модуля не взято: подмена клиентского флага «официальный MM-сервер» (`g_pGameRules + 124`,
Windows), который срезает roll. Нам он не нужен — играем только на `-insecure` комьюнити-серверах,
там флаг и так снят. Если понадобится, нужен свой сигнатурный скан под `client.so` и свой офсет.

## Зарядка и ощущение управления (07.11)

Зарядка — это пропуск вызова `CL_Move`. Вместе с командой не создаётся ничего: **не опрашивается
мышь и не идёт предсказание**. 13 пропусков подряд — это 200 мс, на которые замирает не только
персонаж, но и камера, и весь ввод. Именно это чувствуется как «дёргает и не даёт двигаться»;
никакое сглаживание позиции это не лечит, потому что дело во вводе, а не в картинке.

Поэтому пропуски размазаны: `exploits.chargeSmooth` — 1 тик из N (по умолчанию 3). Один пропуск —
15 мс, не заметно. Платим частотой окон. На вторую пулю DT не распространяется: там заряд нужен
сразу, и рвётся подряд, как раньше.

Второй рычаг — `exploits.defensiveTicks` (по умолчанию 8), заряд под дефенсив отдельно от второй
пули DT. Серверу для отката хватает промаха больше `sv_clockcorrection_msecs` (~60 мс ≈ 4 тика),
полные 13 не нужны. Меньше заряд → короче зарядка, но и окно короче: полезная длина окна — это
откат минус RTT в тиках.

Своя модель и камера сглаживаются по точной модели (`Smoothing.h::localOrigin`): недобор позиции
при зарядке равен `скорость × заряженные тики`, рисуем себя на эту величину вперёд. На сдвиге заряд
обнуляется ровно тогда, когда прыгает позиция, — сумма не меняется, рывка не видно. Когда заряда
нет, смещения тоже нет. Прошлая версия вместо этого прибавляла `velocity × dt` каждый кадр и
подтягивалась с τ 0.3 с: в равновесии картинка постоянно уезжала вперёд на `velocity × τ` (~75 ед.).

## Extended yaw: что показал лог 07.11

Первая рабочая версия дала разброс «взгляд ↔ LBY» от +34 до +180 при заданных 92°. Причина —
билдер крутил yaw модификатором между чокнутой и отправленной командой, и LBY вставал по случайному
углу. Теперь extended yaw, как и roll, делает углы статичными (`noOffset`/`noModifier`/`noSnap`,
десинк по инвертеру) — LBY встаёт ровно на заданный угол.

Порог сервера — скорость > 0.1. Трение гасит за тик всё ниже ~6.5 ед/с, поэтому установившаяся
скорость от микродвижения = `sv_accelerate × forwardmove × интервал` ≈ `0.086 × forwardmove`:
нужно `forwardmove` > 1.16. В lua Persistence стоит 0.1, но там это доли max_speed. Ставим 5
(12 в приседе — wishspeed режется на 0.34), знак через тик. Плюс `movement::fixMovement` срезает
кнопку движения, если компонента < 1, — на неё рассчитывать нельзя, важна только величина.

## Дефенсив после переписывания с нуля (07.11)

Всё, что было написано про дефенсив в разделах выше, устарело: механизм остался, политика
переехала в отдельный модуль и правила стали другими. Актуально это.

### Разделение

`Tickbase.cpp` — только механизм. Он умеет три вещи: пропускать вызовы `CL_Move` (это и есть
зарядка), выдавать накопленные команды пачкой (`requestShift`) и считать сырой откат тикбейса
(`rawDeficit`). Никаких триггеров, окон и «готов/не готов» в нём больше нет.

`Defensive.cpp` — политика. Решает, когда копить, когда рвать и сколько тиков после рывка
считать защищёнными. Вызывается из `Endpoints.h` каждый `CreateMove`, после `movement::exploits`.

`AntiAim.cpp` только спрашивает: `defensive::windowLeft()`, `windowLength()`, `windowCounter()` —
и по ним рисует скрытые углы. Сам он окон больше не запрашивает.

### Почему импульсы, а не цикл

В Neverlose `force_defensive` ставится не каждый тик, а на одной команде из `mode_duration`
(по умолчанию 8) и только при полном заряде. Это принципиально: заряд — это пропущенные команды,
то есть замерший персонаж. Непрерывный цикл «рывок → зарядка → рывок» означает, что управление
отсутствует половину времени — ровно то, из-за чего играть было невозможно.

Поэтому здесь: рывок только при полном заряде, только когда прошлое окно закрылось и только
если с прошлого рывка прошло не меньше `interval` тиков (ползунок «Интервал между рывками»).

### Длина окна больше не угадывается

Раньше окно считалось равным заряду. Это неверно: на сколько сервер откатит тикбейс, зависит
от `sv_clockcorrection_msecs` и от того, как сервер обработает пачку, а не от того, сколько
мы накопили. Теперь после каждого рывка 16 тиков пишется пик `rawDeficit()`, усредняется
(α = 0.3) и именно это значение становится длиной следующих окон. В логе:

```
[дефенсив] рывок 7: сервер откатил 5 тик., в среднем 4.8 (замеров 7)
```

Если там стабильно 0 — сервер не откатывает вовсе (заряд мал или конфиг сервера другой), и
скрытые углы в это время не защищены ничем. Меню показывает это прямым текстом.

### Зарядка размазана

`setDefensiveCharge(target, spread)`: пропускаем 1 тик из `spread`. Один пропуск — 15 мс, его
не видно. 10 пропусков подряд — 150 мс без управления, это чувствуется как рывок. Ценой того,
что зарядка идёт в `spread` раз дольше, движение остаётся нормальным.

### Триггеры

`Пик` — трасса на `peekTicks` тиков вперёд от предсказанных позиций обоих (враг вот-вот нас
увидит), плюс «враг только что нас увидел»; `Пока видят`; `Враг рядом` (< 2000 юнитов);
`По клавише`; `После выстрела` (по росту `m_iShotsFired`, рывок вне очереди). Заряд копится
не только под висящий триггер, но и просто пока рядом живой враг, — иначе первое окно всегда
опаздывает на всю зарядку.

## Анимфикс (07.11)

До этого скелет записи лагкомпа собирался так: у живого врага подменялись две позы
(`body_yaw` формулой `(взгляд − ноги + 60) / 120`, `move_yaw` от скорости), ставился абсолютный
угол, сбрасывался кэш костей — и у игры просился `SetupBones`. Это давало верный разворот ног,
но всё остальное в скелете оставалось **от текущего кадра**: фаза шага, присед, прыжок, lean,
доворот позвоночника, анимация оружия. На бектреке 10 тиков назад (150 мс — полшага бегущего)
хитбоксы рук, головы и корпуса стояли не там, где они были на сервере в том тике.

Теперь скелет строится из **снимка серверной анимации** (`Resolver.h: AnimSnapshot`):

1. Резольвер на `NET_UPDATE_POSTDATAUPDATE_START` сохраняет базу обновления — состояние animstate,
   с которого в этом обновлении начинал сервер (тень прошлого обновления), сетевые слои, взгляд и
   дельту времени (`PlayerState::baseState`).
2. Рейджбот просит у него прогон под нужный угол ног: `resolver::simulateAt(index, …, footYaw, out)`
   ставит базу, зовёт тот же движковый `CCSGOPlayerAnimState::Update` и снимает всё, что прогон
   записал — animstate (0x3b8), 13 слоёв, 24 позы и угол ног, на котором движок остановился
   (он сам обрезает его по максимальному десинку).
3. `Ragebot.cpp: rebuildFromSnapshot` ставит врагу этот снимок, сбрасывает кэш костей, берёт
   `SetupBones` и возвращает всё как было.

Позы больше не считаются формулой — их считает сам animstate, а значит в скелете появляются lean
(слой 12), доворот корпуса, наклон по pitch и правильная фаза движения. Присед и прыжок приходят
из `duckAmount` внутри снимка, а не из текущего состояния врага.

Строятся так все три скелета записи: `±maxDesync` для безопасных точек и угол от резольвера для
самого выстрела. База живёт только на том обновлении, где резольвер разбирал этого игрока
(`canSimulate`): дальше она устарела бы, и прогон шёл бы от чужой фазы анимации. Нет базы —
работает прежний путь (подмена поз), не вышел и он — поворот готовых костей вокруг оси игрока.

В логе выстрела такой скелет помечен `[анимфикс]` — по нему видно, какой путь реально сработал.

Что осталось не сделано: предсказанная запись («вперёд») наследует скелет свежей и только
сдвигается по позиции — фаза анимации в будущее не прогоняется. За 2-3 обновления (30-50 мс) она
уезжает немного, а главный источник промахов там другой — сторона десинка в будущем.

## Перебор вариантов резольвера (07.11)

Было: два режима коррекции (`слои` / `зеркало`) и счёт по попаданиям-промахам на игрока; зеркало
включалось, только когда обгоняло слои на два очка. Плюс отдельный счётчик `extreme` — «доводить
угол до максимума». Против незнакомого антиаима это значило три-четыре промаха подряд **одним и
тем же** углом, пока счёт накопится.

Стало — пять вариантов (`Resolver.cpp: enum Variant`):

| вариант | угол ног |
|---|---|
| `слои` | как нашли |
| `зеркало` | −дельта |
| `до максимума` | полный десинк по найденной стороне |
| `зеркало до максимума` | полный десинк по обратной стороне |
| `по взгляду` | 0 (враг не десинкает, слои врут полностью) |

У каждого свой счёт по игроку — это долгая память (чей антиаим как резольвится), она переживает
дормант и половинится между раундами. Поверх неё быстрый перебор: каждый промах **по вине
резольвера** сдвигает `cycle` на один шаг по порядку предпочтения, попадание перебор останавливает
и закрепляет вариант. Любой вариант, кроме слоёв, должен обогнать их на два очка — один промах по
чужой вине (пинг, стена, чужой дефенсив) угол не переворачивает.

Доказанный промах «сторона верна, ноги дальше» (`onMagnitudeMiss`) больше не крутит отдельный
счётчик, а ставит перебор ровно на `до максимума` той же стороны.

Пока перебор идёт, рейджбот снижает надёжность головы на 30% (`bruteforcing()`): тело ошибку в
стороне прощает, голова — нет.

Угол по LBY (`anchored`) перебор не трогает: там сервер сам показал угол ног.

## Фейклаг: режимы (07.11)

Было одно число — сколько тиков держать команды в чоке. Стало четыре режима
(`HvhConfig.h: FakeLagMode`, считает `Tickbase.cpp: chokeLimit`):

- **Статика** — ровно столько тиков, сколько на ползунке (как было).
- **Случайно** — на каждый чок свой лимит от 1 до ползунка: ровный рисунок чока враги читают и
  подстраивают под него бектрек.
- **Адаптивный** — максимум, при котором шаг за чок остаётся под 64 юнитами по горизонтали.
  Дальше сервер считает шаг телепортом (`CLagCompensationManager`, `m_flTeleportDistanceSqr`) и
  запись лагкомпа по нам не интерполирует.
- **Ломать лагкомп** — наоборот, перешагнуть эти 64 юнита. На земле скорости не хватает
  (250 ед/с — это ~4 юнита за тик на 64 тиках, 64 юнита не набираются и за 14 тиков), так что
  режим работает в полёте и на распрыжке. Меню об этом пишет прямым текстом.

Плюс свои лимиты по состоянию: «в воздухе» (там чок почти не виден — позиция и так летит) и
«пока стоим» (длинный чок — главный способ развести бектрек врага). Ноль — как основной лимит.

При включённом DT фейклаг по-прежнему ограничен одним тиком: серверу нужен запас под сдвиг.

## Антиаим: внутренности (переписаны 07.11)

Снаружи ничего не поменялось — поменялось то, как тик считается. Было: один проход на ~380 строк,
в котором права билдера описывались тремя флагами (`noOffset` / `noModifier` / `noSnap`) и
`std::optional<int> forceDesync`. Эти четыре вещи переписывались в **восьми** местах подряд
(легит, фристенд, edge yaw, ручной, safe head, roll, extended yaw, скрытые углы), так что
побеждал тот режим, что стоял ниже в тексте, а приоритет нигде не был записан. Каждый новый
режим добавлялся ещё одной записью флага.

### Три стадии

```
план  →  поза  →  применение
```

**План** (`buildPlan`) — кто владеет углами в этом тике. Владельцы перечислены по возрастанию
силы, и `claim()` только ужесточает права: статику уже не снять, запрет скрытых углов не
отменить, а сторону десинка задаёт сильнейший из тех, кто её требует.

| владелец | базовый yaw | права |
|---|---|---|
| `Builder` | камера / назад / на врагов | всё можно |
| `Freestand` | на врага + сторона укрытия | статика по галке; сторону тела задаёт сам |
| `Edge` | лицом в стену | статика + полный десинк по инвертеру (по галке) |
| `Manual` | камера ±90 / 180 | то же |
| `SafeHead` | — | статика, **десинк выключен** |
| `Roll` | — | статика, без скрытых углов, десинк по знаку наклона |
| `Extended` | — | статика, без скрытых углов, десинк по инвертеру |
| `Legit` | настоящий взгляд | статика, без скрытых углов, десинк остаётся |

**Поза** — то, что уходит на сервер, и главное: **десинк это ПАРА углов, а не одно число**.

```cpp
struct Pose {
    float pitch, roll;
    float fakeYaw;   // отправленная команда: её видят враги, по ней сервер ставит голову
    float realYaw;   // чокнутые команды: за этим углом сервер тянет ноги
    int   side;       // сторона увода (+1 влево, −1 вправо, 0 — без десинка)
    float desync;     // увод тела в градусах, уже обрезанный по максимуму стойки
};
```

Раньше пары не было: в команду писался один `yaw`, а «настоящий» получался тем, что на чокнутом
тике к нему **дописывалась добавка** в конце функции. Теперь оба угла считаются явно, а
`применение` — одна строка:

```cpp
cmd->viewangles.y = std::remainder(f.sendPacket ? pose.fakeYaw : pose.realYaw, 360.0f);
```

### Что это починило

**1. Модификатор разводил чокнутую и отправленную команды.** `phase` увеличивался на
`sendPacket`, то есть на **последнем** тике цикла чока: предыдущие (чокнутые) тики несли старую
фазу, отправленный — новую. С джиттером на 26° это значит, что к уводу тела молча прибавлялись
те же 26°. Со спином было хуже: `spinYaw += spinSpeed` шагал **каждый** тик, и разница между
чокнутым и отправленным углом равнялась шагу спина. Натуральность (`blended`) плыла по
`realtime` — тоже каждый тик. Теперь настройки состояния, модификатор и сторона замораживаются
на весь цикл чока (`cycleState`, `cycleModifier`, `pinnedSide`), а переключение фазы считается
по циклам, а не по пакетам — «задержка» билдера в них и измеряется.

**2. Ползунок десинка значил не градусы.** Чокнутый угол уводился на `min(величина × 2, 120)`,
поэтому всё от ~29° и выше упиралось в максимум стойки, и половина шкалы ничего не делала. Теперь
цель обрезается по `localMaxDesync()` — тому же `getMaxDesyncAngle()`, который считает сервер
(присед и скорость его режут, поэтому «58» в воздухе значит меньше), а чокнутый угол уводится на
`цель + 12°`: запас нужен, потому что ноги доводятся не мгновенно, но он больше не умножает саму
цель.

**3. Инвертер и фристенд ломали десинк на тик.** Сторона считалась каждый тик, так что нажатие
инвертера или переворот фристенда посреди цикла давали чокнутый и отправленный углы с разных
сторон — на этот тик тело уезжало не туда. Теперь сторона выбирается один раз на цикл.

**4. Индикатор стороны врал.** При safe head (`forceDesync = 0`) ветка десинка целиком
пропускалась, и `desyncSide()` продолжал показывать прошлую сторону как рабочую. Теперь
`pose.side == 0` — это явное «десинка нет».

**5. Скрытые углы дефенсива не замирали до конца.** Они выставляли `noOffset`/`noModifier`, но
сторона десинка на этих тиках всё равно джиттерилась, а добавка «голова за телом» всё равно
прибавлялась. Теперь скрытый угол, забравший `yaw`, переводит план в статику целиком.

### Что осталось как было

Физика не менялась: гистерезис фристенда (3 тика на смену, 8 на удержание), 4-шаговая эвристика
укрытия, edge yaw, safe head по углу обзора врага, микродвижение под extended yaw (5 / 12 ед. на
чокнутой команде, ноль на отправленной) и ±1.1 / 3.25 «чтобы LBY не обновлялся» без него, лог
`[extended yaw]` раз в секунду, флики, анти-брутфорс, стойка пресетов.

### Что знаем и пока не делаем

Стоя без extended yaw десинк всё равно слабый: LBY обновляется раз в ~1.1 с и встаёт на
**отправленный** угол, то есть ноги показывают туда же, куда голова. Микродвижение ±1.1 ед.
держит сервер в «стоячей» ветке, но таймер это не отменяет. Полноценный ломатель LBY — это тот же
механизм, что extended yaw, только с углом по ползунку десинка; смысл включать его автоматически
есть, но тогда стоя пропадёт джиттер головы, и без замера в игре непонятно, что лучше.

## Дефенсив: переписан с нуля (07.11, второй раз)

Первая версия 07.11 поставила правильную политику (заряд заранее, рывок импульсом), но модель окна
в ней была догадкой. Переписано целиком — `Defensive.cpp` плюс то, что к нему относится в
`Tickbase.cpp`.

### Окно — это две разные вещи

Раньше окно было одним числом «тиков осталось». На самом деле защищённых тиков два вида:

| часть | откуда защита | бывает ли на любом сервере |
|---|---|---|
| **тики внутри пачки** | рывок прогоняет заряженные команды подряд, сервер пишет лагкомп **только по последней** — углы остальных он не записывает вовсе | да, всегда |
| **тики после пачки** | наш `m_nTickBase` ушёл в будущее, сервер отбрасывает записи по нам, пока не догонит | **нет**: на сборках с DT-фиксом откат нулевой |

Теперь это два отдельных источника: `tickbase::shiftLeft()` для первой части, замер отката — для
второй.

### Главный баг: окно съедал сам рывок

Внутри сдвига `CL_Move` вызывается по разу на каждую прогоняемую команду, то есть `CreateMove` —
и `defensive::update` — тоже. А update на каждом вызове делал `--window`. Рывок на 10 тиков
открывал окно на 10 и **тут же выжигал его десятью своими вызовами**: к моменту, когда пачка
дошла до сервера, окно уже было закрыто, и скрытые углы на настоящих защищённых тиках не
показывались ни разу. Там же, в тиках пачки, десять раз подряд шёл полный обход игроков с
трассировками и десять раз тикал интервал между рывками.

Теперь первое, что делает `update`:

```cpp
if (tickbase::isShifting()) {
    const int inPack = tickbase::shiftLeft() + 1;
    if (shiftWindow == 0) { length = inPack + expectedRollback(inPack); ++counter; }
    shiftWindow = inPack;
    return;      // тики пачки — не тики времени
}
```

### Окно открывается по факту, а не по догадке

Было: `windowAt = tickbase::chargedTicks()` — заряд, прочитанный **до** `requestShift()`, тогда
как сам сдвиг происходит позже, в конце того же `clMoveHook`, и к тому моменту заряд мог
измениться. Теперь `requestShift(0, true)` помечает сдвиг дефенсивным, тикбейс после пачки
кладёт её настоящую длину, а дефенсив забирает её на следующем тике:

```cpp
if (const int shifted = tickbase::takeDefensiveShift(); shifted > 0) { … }
```

### Сервер проверяется, а не предполагается

Откат виден только по `m_nTickBase` из снапшота, то есть с опозданием на пинг. После каждого
рывка модуль ждёт дедлайн (`пинг туда-обратно / интервал + 6`, раньше — фиксированные 16 тиков) и
берёт пик отката. Дальше:

* **откат есть** — окно продлевается по факту (`left = max(left, deficit)`), среднее учится;
* **откат нулевой** — окно закрывается немедленно, а после трёх пустых рывков подряд ставится
  вердикт «сервер не откатывает»: заряд больше не жжётся, и через 30 секунд модуль пробует снова
  (карта или cvar могли смениться).

И главное — `windowLeft()` больше не врёт:

```cpp
if (shiftWindow > 0) return shiftWindow;              // пачка защищена всегда
return verdict == RollsBack ? left : 0;               // откат — только если он подтверждён
```

До этого на сервере с DT-фиксом дефенсив «работал»: окно открывалось по догадке, и AA честно
показывал туда свои злые углы — ничем не защищённые, то есть бесплатный хедшот врагу.

### Откат от чужого сдвига берётся даром

Телепорт автопика и вторая пуля DT тоже уводят тикбейс. Раньше это окно просто терялось. Теперь,
если сервер уже проверен и `rawDeficit() > 0` без нашего рывка, окно открывается по факту — за
бесплатно, без заряда.

### Пик ловится раньше

Было: одна точка прогноза в конце горизонта (`velocity * ahead`) — на старте выхода из-за угла
скорость ещё нулевая, и триггер срабатывал ровно тогда, когда нас уже увидели. Теперь к прогнозу
добавлен ввод (`driftVelocity`: середина между текущей и желаемой скоростью) и проверяются три
точки по пути, а не одна.

### Заряд перестал дёргать управление на пустом месте

`near` считался как «враг ближе 2000 единиц» — это полкарты, то есть заряд копился практически
всегда, и пропуски тиков шли непрерывно. Теперь радиус 1200, а `spread` адаптивный: пока висит
повод — по ползунку, когда рядом просто кто-то есть — вдвое реже.

### Стадии и чистка

`update` разложен на четыре стадии с явными ролями: **затвор** (можем ли работать), **окно**,
**повод** (наблюдение + биты триггеров), **решение** (заряд и рывок). В `Tickbase.cpp` условие
зарядки — выражение из пяти строк с тремя отрицаниями — разложено в `chargeAllowed()` по причинам.
Убраны: мёртвый флаг `lcShift`, который никогда не выставлялся в `true` (из-за чего лог сдвига
печатался на каждый рывок, включая дефенсивные), мёртвая настройка `exploits.defensive`, мёртвая
`wasKeyDown`.

Для меню добавлена `defensive::statusLine()` — что модуль делает прямо сейчас («Заряд 7 из 10
тик.», «Интервал: ещё 3 тик.», «Окно: 9 тик. (сервер подтвердил)», «Сервер тикбейс не
откатывает…») — и `defensive::verdict()`.

## Движение при дефенсиве: остановки и отдача назад (07.11)

Жалоба: «иду с дефенсивом — из-за плавности останавливаюсь, и меня кидает назад».

### Откуда это бралось

Заряд был устроен единственным способом — **пропуском вызова `CL_Move`**. На пропущенном тике
команда не создаётся вовсе: мышь не опрашивается, предсказание не считается, персонаж на этом тике
никуда не идёт. «Плавность зарядки 1 из 3» означает буквально, что **каждый третий тик движения
выброшен** — то есть треть скорости. Это и есть «останавливаюсь».

«Кидает назад» — вторая половина той же схемы. Рывок прогоняет всю пачку за один реальный тик
(цикл `while` с `callOriginal`), клиент предсказывает 13 тиков движения мгновенно и улетает вперёд.
А сервер обрабатывает за свой тик не больше `sv_maxusrcmdprocessticks` команд — на HvH-сборках это
часто 8, — остальные выбрасывает. Позиция на сервере оказывается позади предсказанной, приходит
снапшот, и коррекция предсказания тянет игрока назад.

### Заряд чоком

Добавлен **стиль заряда**, по умолчанию «Чоком»:

| | чоком (по умолчанию) | пропуском (как было) |
|---|---|---|
| команда на «заряжаемом» тике | создаётся, просто уходит позже | не создаётся вовсе |
| движение и мышь | как обычно | тик потерян |
| что отстаёт | серверная модель — на длину чока | наша собственная |
| окно | каждая отправленная пачка | рывок по требованию |
| «интервал между рывками» | не нужен: интервал = длина чока | нужен |

Это ровно то, чего мы хотим от дефенсива: расхождение между нами и сервером остаётся, но живёт оно
в серверной модели, а наш игрок едет ровно. Пачка из N команд, которую сервер обработает за один
свой тик, даёт ту же дыру в истории лагкомпа, что и рывок, — лагкомп он запишет только по последней
команде пачки.

Реализация: `tickbase::setDefensiveChoke(n)` поднимает `chokeLimit()` до `n` (выше фейклага
билдера), а когда пачка уходит, тикбейс сам сообщает её длину дефенсиву — тем же
`takeDefensiveShift()`, что и при рывке, так что замер отката и модель окна не изменились.

#### Чок и DT

Первая попытка запретила чок при любом включённом DT — и это обнулило всю правку для всех, у кого
стоит галка DT: они остались на пропусках, с теми же остановками и отдачей, да ещё и с «заряд
0-10%» в меню, потому что процент считался по настройке стиля, а не по фактическому режиму.

Разделено правильно:

* **DT «Быстрая стрельба»** — дефенсив молчит, как и раньше: заряд принадлежит второй пуле, а
  пачка «чок + сдвиг» была бы длиннее, чем сервер обрабатывает за раз. Это отсекает
  `defensiveAllowed()`.
* **DT «Дефенсив»** — чок работает. Этому режиму собственный заряд не нужен: тратить его было
  некому, кроме рывков дефенсива и телепортов.

Заодно исправлено `wantCharge()` в тикбейсе. Там стояло «включён DT — значит копим», так что
пропуски шли от одной галки DT, даже когда тратить заряд было некому. Именно они и давали
остановки, хотя чок к этому отношения не имел. Теперь заряд пропусками нужен только для: второй
пули DT, телепорта по клавише, телепорта автопика и дефенсива в стиле «пропуском».

### Потолок пачки читается с сервера

`sv_maxusrcmdprocessticks` — серверный cvar, и на удалённом сервере клиент его обычно не видит.
Если видит (реплицирован или локальная игра) — держим в чоке `limit - 1` команд. Если не видит —
**7**, то есть пачку в 8 команд: столько проходит и там, где лимит урезан до 8. Это и есть источник
«иду вперёд, останавливаюсь, и чуть-чуть назад»: хвост пачки, который клиент предсказал, а сервер
не применил. Раньше про этот лимит знал только фейкдак, и то косвенно — он уменьшал свой чок, когда
замечал, что сервер выкинул хвост с приседом (`m_flDuckAmount` на отправке оказывался нулевым).

### cl_smoothtime: отменено, было хуже болезни

Была попытка размазать рывки через `cl_smooth` / `cl_smoothtime 0.5` на время эксплойтов. Это
ошибка, и её откатили в тот же день. `cl_smoothtime` — это время, за которое клиент **догоняет**
серверную позицию, то есть всё это время своя модель и камера едут в прошлом. С дефенсивом
расхождение держится не вспышками, а постоянно, поэтому полсекунды сглаживания превратились в
постоянное отставание себя от себя — «моделька идёт не со мной, я это не я, а я то, что раньше».
Рывок длится тики, а отставание длилось полсекунды.

Правильное лечение рывков — не создавать их: заряд чоком, на котором команды не теряются вовсе.
`exploitTuning()` остался только для чтения `sv_maxusrcmdprocessticks`, и при первом вызове он
возвращает `cl_smoothtime` с 0.5 на 0.1, если видит ровно наше значение: cvar архивный, и оно могло
уехать в `config.cfg`.

### Чок держится под порогом телепорта

Длина пачки в движении — это один большой шаг за один серверный тик. Больше 64 юнитов сервер
считает телепортом (`m_flTeleportDistanceSqr`) и запись лагкомпа по нам уже не интерполирует, а своя
модель на экране расходится с серверной тем сильнее, чем длиннее чок. Дефенсивный чок теперь
ограничен тем же `ticksForDistance(62)`, что и режим фейклага «Адаптивный»: на земле он почти не
режет (10 тиков бега — это 39 юнитов), а на распрыжке и в полёте сам становится короче.

## Почему дефенсив «не работал» вовсе (07.11, разбор по конфигу)

Две итерации правок не помогли, потому что я чинил не то. Разбор конфига игрока (`~/Osiris/eclipse-ext`)
показал причину сразу: `Exploits."Double tap": true`, `"Double tap mode": 0` — **быстрая стрельба**.

```cpp
bool defensiveAllowed() noexcept
{
    return active && !fakeDuck && isInstalled() && !fastFire();   // ← вот тут
}
```

То есть у всех, кто играет со второй пулей, дефенсив был **выключен целиком** и честно показывал
«DEF 0%». Ни стиль заряда, ни модель окна к этому отношения не имели.

### Окна от чужих сдвигов

Запрет был оправдан только наполовину: свои рывки при быстрой стрельбе правда невозможны — заряд
принадлежит второй пуле, а пачка «чок + сдвиг» вышла бы длиннее, чем сервер обрабатывает за один
свой тик. Но **сдвиг на выстреле даёт настоящий откат**, и окно в нём такое же, как от нашего
рывка. Раньше это окно просто терялось.

Теперь `takeDefensiveShift()` стал `takeShiftPack()` и отдаёт длину **любой** ушедшей пачки — рывка
дефенсива, второй пули DT, телепорта автопика. Дефенсив ловит её, меряет откат как обычно и
показывает в окне скрытые углы. При быстрой стрельбе он работает именно так, и меню это пишет:
«Быстрая стрельба DT: свои рывки нельзя, ловим окна от её сдвигов».

### Триггер «пик» в режиме «чоком» не срабатывал никогда

```cpp
const bool wantPeek = (cfg.triggers & DefPeek) && tickbase::chargedTicks() >= chargeTarget && left == 0;
```

Условие про полный заряд осталось с прежней схемы. В режиме «чоком» заряда нет по определению —
значит трассы пика не считались, `sight.peeking` всегда был false, и дефенсив открывал окна только
когда нас **уже** увидели (`DefVisible`), то есть с опозданием на весь смысл фичи. Теперь условие
зависит от способа: чоком — окно открывается сразу, пропуском — нужен полный заряд, при быстрой
стрельбе своих окон нет.

### Остановки при DT: зарядка рвала подряд

```cpp
if (fastFire() && !defensiveRecharge)
    return true;    // «заряд нужен как можно быстрее, рвём подряд»
```

13 пропущенных вызовов `CL_Move` подряд — это 200 мс, на которые персонаж просто стоит, а потом
предсказание догоняет сервер рывком. Вот и «иду вперёд, останавливаюсь, и чуть-чуть назад», причём
без всякого дефенсива — достаточно одной галки DT.

Теперь пропуски идут подряд **только когда мы стоим** (там их не видно вовсе: идти всё равно
некуда), а в движении размазываются по тому же ползунку «Плавность зарядки», с минимумом 3 для
второй пули. Заряд в движении набирается втрое дольше — зато бежать при этом можно. Ползунок
перестал скрываться в режиме «чоком»: он задаёт плавность и для заряда DT.

## Разбор скриншота 07.11: четыре жалобы, две из них — баги

### Заряд копился постоянно из-за НАЗНАЧЕННОЙ клавиши

`wantCharge()` включал заряд, если `teleportKey.isSet()` или (с DT) `autoPeekKey.isSet()` — то есть
достаточно было назначить клавишу, и заряд копился всегда, даже когда её никто не нажимал. В
конфиге игрока `Auto peek key: V` и DT на MOUSE4, так что при включённом DT бег по пустой карте шёл
с пропуском каждого третьего тика — отсюда «иду вперёд, останавливаюсь».

Теперь `chargeAllowed()` отделяет «заряд в принципе нужен» от «нужен прямо сейчас»:

* **стоя копим всегда** — пропущенная команда там не видна вовсе, идти всё равно некуда;
* **на ходу** — только если есть в кого стрелять второй пулей (`threat` или цель у рейджбота),
  нажата клавиша телепорта или автопика, либо дефенсив копит под своё окно.

### «DEF 0%» читалось как поломка

При заряде чоком «процент» почти всегда 0: заряда как сущности там нет, есть накопленный чок,
который появляется только по триггеру. Красный «DEF 0%» на пустой карте выглядел как сломанный
модуль, хотя дефенсиву просто не на кого открывать окно. Индикатор теперь говорит словами:
`DEF ЖДЁТ` (тускло) · `DEF 12%` · `DEF ОКНО` · `DEF НЕТ ОТКАТА`.

### Что оказалось не багом

**Двоящаяся и «изломанная» модель** — это включённая настройка Вид → «Модель сервера»
(`View."Server model": true`, голубой полупрозрачный силуэт). Она рисует вторую копию модели,
повёрнутую на угол десинка: ноги на серверный `footYaw`, корпус плавно к отправленному взгляду,
голова по взгляду. При десинке под 58° руки и оружие двух копий расходятся сильнее всего — отсюда
ощущение «четырёх рук». Это и есть её работа: показать, какую позу видит враг. Выключается там же.

**Поза с руками вниз и наклоном вперёд** — это `Pitch: вниз` из антиаима. В третьем лице свой AA
так и выглядит.

## Сглаживание своей модели убрано целиком (07.11)

Было: `hvh::smoothing::localOrigin()` рисовал свою модель и камеру на `velocity × chargedTicks ×
interval` вперёд (с потолком 40 ед. и подтяжкой с τ 0.05 с), сдвиг лежал в `localOffset` и
применялся в трёх местах — к костям в `DrawModelExecute`, к костям viewmodel, к камере в
`overrideView`, плюс как pivot у «модели сервера».

Почему убрано. Сдвиг у себя не бывает согласованным: кости модели двигаются в `DrawModelExecute`,
камера — в `overrideView`, руки — в `CalcView` (ещё раньше), трассы и предсказание — вообще не
двигаются. Любое место, куда сдвиг не доехал, выглядит как телепорт: именно так уезжало оружие из
руки, пока владелец искался по мёртвому нетвару `moveparent`, и так же расходились руки с камерой.
При этом скрыть рывок сдвига он всё равно не мог: потолок 40 ед. меньше самого рывка на бегу
(14 тиков × 250 ед/с ≈ 55 ед.), так что остаток рывка был виден, но уже вместе с рассинхроном.

Теперь своя модель рисуется ровно там, где её посчитал движок. Рывок при сдвиге видно — он
настоящий, и серверу так и надо. Сглаживание ЧУЖИХ игроков (`smoothing::origin()`, `states`)
осталось: там сдвиг применяется к копии костей целиком, вместе с оружием владельца, и расходиться
нечему.

Удалено: `Smoothing.h` — `localState`, `maxLocalLead`, `localOrigin()`, `localOffset`;
`Endpoints.h` — блок расчёта в `RENDER_START`, сдвиг viewmodel, сдвиг своих костей, оба сдвига
камеры, pivot призрака = `info.origin`; `tickbase::visualCatchUp()` и счётчик `irregularTicks`
(последний читатель был именно он); настройка `view.smoothLocalModel`, её сериализация и галка
«Без телепорта у себя» в меню.

## Почему дефенсив AA работал «иногда» (07.11, разбор по логам)

Жалоба: скрытые углы иногда не показываются, хотя всё настроено. Логи сессии после сборки 21:22
дали точный ответ — 279 пачек за 53 секунды, из них **9 удачных замеров отката (3%)**, серии до
274 «пустых» подряд и в 21:26:21 вердикт «сервер тикбейс не откатывает», при том что в 21:27:48 и
21:27:51 тот же сервер откатил на 8 и 14 тиков.

Корень — в том, как мерился откат. Замер привязывался к пачке: `peak = 0`, `confirmWait =` пинг
туда-обратно + 6 тиков, и пик `rawDeficit()` за это время. Но в режиме «чоком» пачка уходит каждые
7-8 тиков, а ответ сервера приходит через 10-20, и **каждая новая пачка обнуляла пик и
рестартовала дедлайн**. Замер почти никогда не доживал до конца и закрывался как «пусто». Это
видно и по номерам в логе: `рывок 1, 2, 4, 5…` — номер 3 не залогирован вовсе, его замер затёрли.

Дальше шла цепочка: три «пустых» подряд при `samples == 0` ставили вердикт `Ignores`, а
`windowLeft()` при нём возвращает 0 — то есть скрытые углы выключались целиком на 30 секунд. Через
30 секунд вердикт снимался, три пачки снова «не успевали», и всё повторялось. Отсюда «иногда».

Исправлено:

* **замер отвязан от пачки.** Откат ловится непрерывно: `rawDeficit() >= 2` — это эпизод, его пик
  пишется в среднее, когда эпизод кончился. Чья пачка его вызвала и какой пинг — не важно.
  Удалены `confirmDeadline()`, `confirmWait`, `probesFailed`, `closeProbe()`.
* **порог вердикта `Ignores`** — 40 пачек без единого отката вместо трёх «пустых» замеров.
* **`counter` крутится и для чоковых пачек.** Раньше его двигал только блок `isShifting()`, а
  чоковая пачка — не сдвиг, так что в режиме «чоком» номер окна не менялся никогда и рисунки
  скрытых углов, которые от него зависят, стояли на месте.
* **порог длины пачки `packSize >= 3` → `>= 2`** (Tickbase.cpp). Дефолт `sv_maxusrcmdprocessticks`
  в CS:GO — 2, `chokeLimit()` держится под лимитом, значит пачка длиннее двух там и не бывает: на
  таких серверах окно не объявлялось вообще.
* **статус в меню больше не врёт.** «Окно: N тик.» показывается только когда окно действительно
  объявлено; пока откат от сервера ещё не виден — «Пачка прошла, отката от сервера ещё не видели».

Лог стал тише: строка пишется на эпизод отката, а не на каждую пачку.

### Второй повод для «иногда»: счётчик длительности жил через границу окон

`snap.ticks` считает тики внутри окна и сравнивается с «Длительностью». Обнулялся он только в тике,
когда окна нет (`else { snap.ticks = 0; }`). С дефенсивом «чоком» окна идут вплотную, разрыва без
окна может не быть много секунд — счётчик перешагивал «Длительность» и скрытые углы молчали до
первой паузы. Теперь отсчёт сбрасывается по смене `defensive::windowCounter()`, то есть на каждом
новом окне, вместе с `apex`, задержкой джиттера и разыгранными случайными углами.

### Чего в этой жалобе НЕ было

Проверено по конфигу `~/Osiris/eclipse-ext`: все семь состояний скрытых углов стоят в `Mode: 2`
(«Своё»), цепочка `selectSnapState()` → `activeSnap()` для воздуха отрабатывает верно
(`jumping` проверяется раньше `EdgeBait`), `Roll: 0` и `Extended yaw: 0` — то есть `allowSnap`
никто не забирал. Состояние «Воздух» было ни при чём: окна не было вообще, ни в воздухе, ни на
земле, потому что вердикт сервера висел в `Unknown`.

Отдельно стоит помнить: `Owner::Roll` в `buildPlan()` claim-ит с `allowSnap = false`. Если
включить наклон, скрытые углы дефенсива отключатся целиком — это осознанно (наклон требует
статичных углов), но из меню не очевидно.

## Чок дефенсива против пика и рейджа (07.11, вечер)

После того как замер отката починили, вердикт `Ignores` перестал ставиться впустую — и чок начал
работать там, где раньше молчал. Вылезли два следствия, которых до этого просто не было видно:

**Телепорт на выходе из-за угла.** `chokeLimit()` резал пачку по `ticksForDistance(62.0f)`, то
есть держался вплотную под серверным порогом телепорта (`m_flTeleportDistanceSqr`, 64 юнита). Но
64 — это граница, за которой сервер перестаёт интерполировать запись лагкомпа, а не граница
комфорта: шаг в 62 юнита за один серверный тик — почти корпус, и на пике он ощущается как рывок.
Режем вчетверо, до 16 юнитов: на бегу (250 ед/с) это ~4 тика вместо 14.

**Промахи рейджа.** Рейдж целится по тому, где враг сейчас, а выстрел уходит последней командой
пачки — то есть сервер применит его из позиции, до которой мы ещё не дошли. Чем длиннее пачка, тем
больше расхождение. Теперь, пока у рейджа есть цель (`ragebot::currentTarget() != 0`), чок режется
до 2 тиков: окно короче, зато прицел и выстрел сходятся.

Обе правки сознательно размениваают длину окна на управляемость. Дефенсив с окном в 2-4 тика
всё ещё ломает бектрек (сервер пишет лагкомп только по последней команде пачки), а вот
неуправляемый персонаж и мимо летящие пули не стоят ничего.

### Почему спин в воздухе выглядел фликами

Две причины складывались.

**Окно стало слишком коротким.** Правка «при цели — чок 2 тика» выглядела разумно, но в хвх цель
есть практически всегда, так что она урезала пачку постоянно, а не только в стрельбе. Окно равно
длине пачки, значит спин показывался по два тика за цикл — вспышками. Теперь урезание действует
только там, где от него есть польза: на земле, в движении, при наличии цели (`!airborne &&
movingFast`), и до 4 тиков, а не до 2. Стоя шага нет вовсе — расходиться нечему.

**Предел по шагу не различал землю и воздух.** На земле шаг в 16 юнитов оправдан: пик ведут мышью,
и рывки заметны. В воздухе траекторию уже не изменить и пика не бывает, поэтому там предел 40
юнитов — пачка выходит вдвое-втрое длиннее, и спин успевает прокрутиться.

Полностью плавным спин при чоке не станет никогда, и это не баг: сервер получает наши углы один
раз на пачку, значит и враг видит их один раз на пачку. Чем длиннее окно, тем реже сэмплируется
угол. Непрерывное вращение и длинное окно — взаимоисключающие вещи; выбирать между ними можно
ползунком «Заряд» и «Стилем заряда».

## Рейдж с зажатым фейкдаком (07.11)

Жалоба: «если я сижу на ФД, рейдж ужасно стреляет».

В `chokeLimit()` фейкдак возвращает свой лимит (до 14), а в решении об отправке стояло полное
исключение:

```cpp
bool sendThis = (sendNext && !fakeDuck) || choked >= chokeLimit() || choked >= 14;
```

`sendNext` — это просьба рейджа «следующая команда без чока, в ней будет выстрел». При фейкдаке
она игнорировалась начисто: пакет ждал конца цикла, то есть **до 14 тиков, больше 200 мс**. Враг
за это время уезжает, и каждый выстрел уходил по позиции двухсотмиллисекундной давности.

Цикл фейкдака (Movement.cpp) устроен так: первую половину `IN_DUCK` не нажат, вторую — нажат. На
сервере мы в приседе как раз во второй половине, и отпускать пакет там не только можно, а нужно:
эта поза и есть смысл фейкдака. Теперь:

```cpp
const bool duckShotReady = fakeDuck && choked >= fakeDuckChokeLimit / 2;
bool sendThis = (sendNext && (!fakeDuck || duckShotReady)) || choked >= chokeLimit() || choked >= 14;
```

Задержка выстрела падает с 14 тиков до 7 в худшем случае, и выстрел уходит в приседе, а не в
случайной фазе.

Что осталось нерешённым: рейдж вообще не знает про фейкдак (`grep fakeDuck Ragebot.cpp` — пусто).
Он выбирает точку и считает автоволл из текущей высоты глаза, а она при фейкдаке гуляет между 64 и
46 юнитами, и к моменту, когда команда дойдёт до сервера, будет уже другой. Правильнее было бы
дать рейджу ждать нужную фазу самому — тогда он целился бы по актуальной позиции врага, а не по
той, что была полцикла назад.

## Рейдж: стрельба по прогнозным записям (07.11, по статистике логов)

Жалоба: «рейдж уебещный, раньше вроде лучше был». Считаем по логу 07.11 (347 выстрелов):

| запись | попал | промах | хитрейт |
|---|---|---|---|
| стоит | 58 | 8 | 88% |
| свежая | 111 | 33 | 77% |
| старая | 35 | 12 | 74% |
| onshot | 12 | 6 | 67% |
| **вперёд (прогноз)** | **18** | **47** | **28%** |
| экстраполяция | 1 | 2 | 33% |

Итого: по реальным записям 216/59 (79%), по прогнозным 19/49 (**28%**). Прогноз дал 49 из 108
промахов сессии — почти половину, при 20% от всех выстрелов.

Причина не в самом прогнозе, а в том, что его никто не штрафовал на последнем рубеже. `hitchance()`
считает разброс по 256 сидам для ЗАДАННЫХ костей и ничего не знает о том, верны ли сами кости.
Для прогнозной записи кости выдуманы экстраполяцией, и 90% хитшанса там означают «90%, если враг
действительно окажется там», а не «90% попаду». Внутри выбора точки штрафы были (`trust *= 0.6`,
`shrink *= 0.75`), но до порога стрельбы они не доходили.

Теперь порог поднимается прямо в блоке хитшанса:

```cpp
const bool predictedShot = t.kind == RecordKind::Ahead || t.kind == RecordKind::Extrapolated;
const int needChance = predictedShot ? std::min(settings.hitchance + 25, 95) : settings.hitchance;
```

Рейдж чаще промолчит и дождётся настоящей записи, вместо того чтобы стрелять в предполагаемое
будущее. Правка намеренно сделана одной точкой, а не переделкой выбора точек: остальные изменения
коммита c9d590b5 (мультипоинт 6 → 14 точек, бюджет 160 → 240, края капсул) по логам работают —
попадания в голову идут десятками.

## Переделка AA в конфиге eclipse-ext (07.11)

Разбор того, что было: во всех девяти состояниях `Desync left == Desync right == 58`, модификатор
«центр-джиттер» в шести из девяти, размахи до 72°, добавки ровно ±N.

* **Асимметричный десинк.** При 58/58 резольверу нужно угадать только знак — величина известна и
  всегда максимальная, значит «общая точка», накрывающая обе стороны, существует всегда. Разные
  величины по сторонам её убирают: ошибка по стороне теперь даёт ещё и ошибку по величине.
* **Разные модификаторы.** Центр-джиттер — самый узнаваемый рисунок. Раздали по состояниям
  скиттер, джиттер 0/+, N-way, рандом.
* **Размахи урезаны** (72 → 38, 58 → 34, 50 → 30): большой размах мгновенно читается как джиттер,
  а своя голова уезжает от цели так далеко, что рейджу приходится доворачивать.
* **Статика убрана из «Ходьбы» и «Воздух+присед»** — одна сторона на всё состояние это подарок.
* `Fake lag air` 0 → 2 (без чока в воздухе нет и десинка), `Fake lag standing` 3 → 5.

Бэкап: `~/Osiris/eclipse-ext.bak-before-aa-rework`. Скрипт правки — в scratchpad сессии.
